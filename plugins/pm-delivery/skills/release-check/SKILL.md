# Приёмка релиза глазами PO

Цель — до QA-отчёта и жалоб увидеть, где прод расходится с PRD. Только чтение: прод, трекер задач, документы. Ничего не нажимать, что меняет данные (оплата, удаление, отправка, модерация).

## 1. Фичи релиза

- Вход — дата релиза (`ДД.ММ.ГГГГ`) или пути к PRD.
- По дате: эпики в трекере с этим релизом (статус, ссылка на PRD) и локальные PRD с этим релизом — поиск по базе документов из правил проекта.
- Эпик не «Готово» — в отчёт строкой «не вышел», критерии не проверяй.

## 2. Чек-лист

```powershell
node <папка скилла>/scripts/criteria.mjs <PRD.md> [...] > <папка релиза>/Приёмка-релиза-<ДД.ММ>.md
```

Скрипт берёт раздел PRD «Критерии приёмки» (заголовок `## Критерии приёмки` или `## 6. Критерии приёмки`) и ставит тип: `сайт`, `приложение`, `админка`, `аналитика`, `QA`, `позже`.

## 3. Проверка

| Тип | Кто и как |
|---|---|
| сайт | Сначала без входа: публичная страница, HTML и данные страницы (fetch или bb-browser). Вход нужен — ваша сессия в браузере, только чтение. Много проверок — отдать субагенту |
| приложение | Эмулятор или телефон; нет сборки — «не проверено» |
| аналитика | DebugView GA4 или ваша BI-система, если событие уже должно идти; иначе — QA |
| админка, QA | Не проверять самому: строка в список вопросов QA |
| позже | Дата проверки в отчёт |

- Каждая проверка — итог `ок` / `расхождение` / `не проверено` и доказательство: скриншот, кусок HTML, ответ API.
- Личные данные (телефоны, имена, email) в отчёте маскировать.

## 4. Отчёт

В том же файле, сверху:
1. Одна строка: сколько критериев проверено, сколько расхождений.
2. **Расхождения** — таблица: фича, критерий, ожидалось, на проде, доказательство, что делать (баг в трекер / уточнить у QA / правка PRD).
3. **Вопросы QA** — список.
4. **Проверить позже** — с датами.

В чат — ссылка и 1–2 строки. Баги в трекер не заводить без «да» пользователя.
